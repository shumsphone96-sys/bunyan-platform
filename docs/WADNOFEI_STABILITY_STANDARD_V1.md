# معيار استقرار منصة نادي ود نفيع — الإصدار 1.0

هذا المستند هو بوابة القرار قبل أي تطوير أو نشر إنتاجي لمنصة نادي ود نفيع. لا يكفي أن تفتح الصفحة؛ الاستقرار يثبت بالأدلة والاختبارات.

## 1. مستويات القرار
- RED — غير مستقر: خلل حرج، فقد/فساد بيانات، تجاوز صلاحيات، فشل دخول/عضوية/مالية/وثائق، أو غياب نسخة احتياطية قابلة للاستعادة.
- AMBER — مستقر بشروط: الوظائف الحرجة سليمة لكن توجد عيوب غير حرجة أو تحسينات أداء/واجهة موثقة.
- GREEN — مستقر: جميع بوابات P0/P1 ناجحة ولا توجد عيوب حرجة مفتوحة، مع تحقق النسخ الاحتياطي والاستعادة والمراقبة.

## 2. البوابات الإلزامية
### A — الصحة والتوفر
- /health يعيد 200.
- الصفحة العامة، /membership، /club-admin، /constitution تعمل وفق الصلاحية.
- لا توجد 5xx متكررة في المسارات الحرجة.

### B — سلامة البيانات D1
- لا نشر يكتب أو يمسح بيانات إنتاجية دون migration صريح ومراجع.
- الجداول الحرجة موجودة ومتسقة.
- عدد السجلات قبل/بعد النشر موثق للعضوية والمدفوعات والوثائق.
- اختبارات uniqueness/foreign references والقيم المطلوبة تمر.

### C — الهوية والصلاحيات
- الزائر لا يصل لمسارات الإدارة.
- الجلسات المنتهية ترفض.
- الأدوار تطبق أقل صلاحية لازمة.
- العمليات الحساسة تسجل في audit log.
- لا أسرار أو كلمات مرور افتراضية في الواجهة أو السجل أو المستودع.

### D — العضوية
- إنشاء طلب، تتبع الطلب، القبول/الرفض، رقم العضو، منع التكرار، والحالة المالية تختبر end-to-end.
- لا يتحول الدفع وحده إلى عضوية معتمدة.
- لا يعاد استخدام رقم عضو.

### E — المالية
- إيصال مرقم، قيد دخل/مصروف، منع الحذف الصامت، مطابقة الإجماليات، وسجل التدقيق.
- أي إلغاء يبقى أثره محفوظًا.

### F — الوثائق والنظام الأساسي
- /constitution يقرأ الإعدادات من DB.
- PDF صالح ويبدأ %PDF- وبصمة SHA-256 محفوظة.
- القراءة والتنزيل واحترام download_enabled/published تعمل.
- استبدال الملف يسجل actor/action/hash/size.

### G — النسخ الاحتياطي والاستعادة
- نسخة احتياطية حديثة قبل النشر.
- اختبار استعادة فعلي في بيئة غير إنتاجية.
- لا يعتبر وجود ملف backup وحده نجاحًا حتى يثبت restore.

### H — الأداء والموبايل
- لا أخطاء JavaScript مانعة.
- iPhone/Android/desktop: الدخول، القوائم، النماذج، PDF واللوحات قابلة للاستخدام.
- قياس p50/p95 للمسارات الحرجة وتسجيل baseline قبل التحسين.

### I — المراقبة
- health check دوري.
- تسجيل أخطاء 5xx والعمليات الإدارية الحساسة.
- تعريف owner وخط رجوع rollback لكل نشر.

## 3. معيار قبول الإصدار
لا يوصف الإصدار بأنه GREEN إلا إذا:
1. 100% من اختبارات P0 ناجحة.
2. 100% من اختبارات P1 الحرجة للبيانات/الأمن ناجحة.
3. صفر عيوب Critical/Blocker مفتوحة.
4. backup + restore مثبتان.
5. smoke test بعد النشر ناجح.
6. rollback target معروف ومجرب أو موثق بوضوح.

## 4. تصنيف الاختبارات
- P0: health, auth, DB read, membership core, finance integrity, constitution read, backup/restore.
- P1: admin CRUD, audit, permissions, mobile critical flows, exports.
- P2: تحسينات الشكل والسرعة والراحة التي لا تهدد البيانات أو التشغيل.

## 5. قاعدة التطوير
Stabilize → Measure → Improve → Extend.
لا نضيف وحدة كبيرة جديدة قبل إغلاق RED. في AMBER يسمح بتحسينات معزولة لا تمس schema أو البيانات. في GREEN يبدأ التطوير الوظيفي عبر فرع مستقل واختبارات ثم مراجعة ثم نشر تدريجي.

## 6. تقرير كل إصدار
كل إصدار يجب أن يسجل: commit، وقت الاختبار، البيئة، نتائج P0/P1، baseline الأداء، backup id/time، نتيجة restore، العيوب المفتوحة، قرار RED/AMBER/GREEN، وخطة rollback.
